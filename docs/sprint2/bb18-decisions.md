## BC-D029-a — Queue and ordering
For BB-18, active non-superuser STAFF `GET /api/v1/requests` defaults to `status=SUBMITTED`. Optional `status` accepts exactly SUBMITTED, APPROVED, REJECTED, ISSUED and CLOSED; an explicit valid status filters to that status. Filtered rows are sorted by urgency rank CRITICAL, URGENT, ROUTINE, then `created_at` ascending (oldest first), then UUID `id` ascending. Filtering and sorting happen before pagination and count. `page` ≥ 1; `page_size` 1–100, default 20. An empty or beyond-last page returns 200 with `results: []` and a truthful filtered count. Unknown, repeated or invalid query keys return 400. There is no arbitrary client sort and no `requester_id` filter.

## BC-D029-b — Review state machine and reasons
`PATCH /api/v1/requests/{request_id}/status` accepts only `status` APPROVED or REJECTED, and conditionally `rejection_reason`. Only SUBMITTED may transition, and only once. REJECTED requires a string reason, trimmed at both ends, 1–240 characters after trimming; an omitted, null, blank, non-string or too-long reason returns 400. APPROVED requires the `rejection_reason` key to be absent (even explicit null returns 400), and the saved reason remains null. All unknown or read-only keys are rejected with 400. Already-decided, ISSUED or CLOSED requests, including an identical replay, return 422 `invalid_transition` without overwriting history. Review does not change the owner, blood group, component, quantity, urgency or `fulfilled_quantity`. Approval does not reserve or require stock, and does not imply issue or delivery.

## BC-D029-c — Role and authentication gate
The staff queue and review API and direct services require an authenticated, active user with role STAFF and `is_superuser=False`. ADMIN, DONOR, REQUESTER, inactive and anonymous users, and every superuser, have no staff-review access. STAFF does not need the clinical `view_donor_health` permission. Existing same-origin sessions, CSRF for PATCH, and the strict JSON parser, error, correlation and audit conventions are kept. A feature-private pure operational predicate, DRF gate and service guard in `blood_requests` is authorized until a shared helper is integrated. There are no clinical gate changes and no duplicate denial audits.

## BC-D029-d — Atomic decision history and migration
`review_request` owns `transaction.atomic`, locks the existing BloodRequest with `select_for_update`, rereads the SUBMITTED state after the lock, then atomically saves the status, `rejection_reason` and server-side reviewer and time metadata. `reviewed_by` (nullable `AUTH_USER_MODEL` FK, PROTECT) and `reviewed_at` (nullable aware DateTimeField) are added to the existing BloodRequest through a new Django-generated migration. Both are set for every new successful BB-18 decision. Older rows stay null when history is unknown; no reviewers are invented or backdated. The existing requester PROTECT and the quantity and fulfilled constraints are kept. The response stays the existing BloodRequest DTO; the metadata is internal for now. There is no ordinary endpoint to overwrite or delete a review. Concurrent review requests produce exactly one committed decision and one 422 after the lock; failures roll back all decision fields.
