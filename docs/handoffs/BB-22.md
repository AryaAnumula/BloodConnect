## Public Python interfaces (provided by Arya)

`notification_adapter.services.intents.enqueue_intent(*, event_id, recipient_id, event_type, record_id, due_at, channels) -> {id,event_id,state}`

- Caller owns outer transaction.atomic, which must also save the business record. Never call after commit or from on_commit: a failed enqueue must roll back booking too.
- UUID IDs; recipient_id is ACCOUNT UUID, not DonorProfile UUID. UTC-aware datetime; event_type one of NEAR_EXPIRY/LOW_STOCK/APPOINTMENT_REMINDER/APPOINTMENT_CANCELLED; unique nonempty channels from IN_APP/EMAIL_MOCK/SMS_MOCK.
- Durable DB insert only, no network. Same event ID and identical normalized payload returns same intent; conflicting payload raises EventConflict. Other exceptions: DecisionRequired, ValueError, RuntimeError, database errors. Do not swallow persistence failures.
- Used by inventory BB-15 and scheduling BB-21/22. No circular imports: caller imports provider, provider never imports scheduling at module load.

`notification_adapter.services.reminders.schedule_appointment_reminder(*, appointment_id, donor_user_id, starts_at, booked_at, channels=None) -> {id,event_id,state,due_at,late_booking}`

- Same caller transaction as confirmed booking; both S2-06 and S2-07 required.
- Deterministic event ID for appointment + starts_at. Starts_at and booked_at aware timestamps, starts_at > booked_at. Default channel IN_APP is a persisted MOCK receipt, not an implemented inbox.
- Proposal: due_at=start−24h if booking is at least 24h ahead; otherwise booked_at with late_booking=true. Immediate late receipt NEVER satisfies 24h criterion.
- Exceptions as enqueue; canceled reminder cannot be silently reactivated. Reschedule: cancel old intents and schedule new start in SAME booking transaction. Reinstating identical canceled start requires an agreed revision/event-key policy; currently blocked, not a fake success.

`notification_adapter.services.reminders.cancel_appointment_reminders(*,appointment_id) -> int`

- Caller cancellation/camp cancellation transaction; cancels pending/blocked/leased intent. Already delivered mock cannot be unsent. Camp owner iterates affected appointments in the same transaction. No appointment model writes in notification module.

`notification_adapter.services.dispatch.dispatch_due(*,now,limit=100) -> counts`

- Run OUTSIDE any outer atomic transaction. Short DB lease transaction, HTTP outside transaction, compare-and-set completion. Counts: delivered/retry/failed/blocked/cancelled/superseded.
- Three actual transport attempts maximum; retries after 60 then 120 seconds. 30-second abandoned lease recoverable. Do not run multiple workers against SQLite; PostgreSQL concurrency has not been verified.
- Source provider unavailable/unapproved: BLOCKED with 60s recheck, no delivery claim. Real HTTP failures use redacted codes, not payloads/tokens.
- Concurrent cancellation during HTTP can occur after dispatch checks. CAS prevents cancellation being overwritten, but an already accepted mock receipt cannot be undone. This is a documented limitation, not an exactly-once guarantee.

## Private HTTP contract

Exact implemented schema: docs/api/notifications.openapi.yaml. Same existing POST /internal/notifications, private service Bearer token, never browser/session credentials. Fields event_id, recipient_id, type, record_id, due_at (aware ISO8601), channels. No free-text health/contact payload. 202 only after durable mock receipt, 400 malformed, 401 unauthorized, 409 conflicting event ID, 413 >16KiB, 501 disabled, 503 storage unavailable. Response event_id, delivery_mode=mock, receipts[{channel,status=DELIVERED}]. Event replay returns original receipt after restart. Single Node process and persistent local/named volume required; not a multi-process clustered service. Tokens and raw events are not stored in receipts. Protect local receipt directory and DB: UUID metadata is still sensitive.

## Timing limitation requiring a decision

Scheduling exactly start−24h is not proof of delivery AT LEAST 24h in advance: polling/network delay can make receipt late. timing_met is measured using actual receipt completion, false for late bookings or receipts. Before final acceptance agree an advance safety margin and dispatch cadence (update contracts/tests with approval), or provide measured on-time delivery evidence for the agreed clock boundary. Do not silently relax the adopted criterion. No fake clock test proves deployment uptime/timing.
