## Migration, races and rollback

- **Clean migration:** the fresh project DB applied `0001` then `0002` successfully. `test_review_migration` migrates to `0001`, inserts BB-17-era rows (SUBMITTED and APPROVED) through the historical model, migrates to `0002`, and confirms `reviewed_by`/`reviewed_at` stay null with nothing invented.
- **Concurrency** (`test_review_concurrency`, `TransactionTestCase`, separate thread connections, PostgreSQL only):
  - Approve and reject released together by a barrier, repeated 5 times: each attempt has exactly one `ok` and one `invalid_transition`, no crashes or timeouts, and the saved status, reviewer, reason and time match the winner.
  - A second test holds the row lock in another connection and checks that the contender is still blocked after 1 s. After release, the contender gets 422, and the first decision stays intact.
- **Rollback:** a `DatabaseError` injected after the save (service and API) returns 503 `storage_unavailable` with redacted details. All decision fields stay SUBMITTED/null, and the service still works afterwards.
- **No overwrite:** replaying the same or the opposite decision returns 422, and the original status, reason, reviewer and time are unchanged. ISSUED and CLOSED requests return 422.

   - requester, donor and admin PATCH return 403 forbidden

   - staff PATCH without a CSRF token returns 403 `csrf_failed`
   - staff POST returns 403 forbidden
7. PostgreSQL readback: the decided rows have `reviewer_role=STAFF`, `reviewed_at` set, quantity unchanged, `fulfilled_quantity` 0 and the owner still the REQUESTER. The undecided rows have a null reviewer.
