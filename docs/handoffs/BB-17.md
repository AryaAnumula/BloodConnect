## Behaviour

- `POST /api/v1/requests` (no trailing slash) → 201 `BloodRequest`. Session authentication and CSRF.
- Allowed only for an authenticated, active, non-superuser `REQUESTER`. Every superuser is denied, including
  one with role REQUESTER; `view_donor_health` grants nothing. Anonymous or deactivated: 403
  `authentication_required`. Other roles: 403 `forbidden`. Exactly one `access_denied` audit event per denial,
  written by the existing `core.errors` handler.
- Body: exactly `blood_group`, `component_type` (WHOLE_BLOOD, RBC, PLASMA, PLATELETS), `quantity` (strict JSON
  integer 1–100, never clamped) and `urgency_level` (CRITICAL, URGENT, ROUTINE). Anything else, including
  `requester_id` and `status`, gets 400 `validation_error`. Malformed or duplicate-key JSON: 400 `invalid_json`.
- The server sets status `SUBMITTED`, `fulfilled_quantity` 0, `rejection_reason` null and the requester from the session.
  Current stock is not required.
- Runtime policy: `config/request-policy.json` (`bb17-college-demo-v1`). Missing or invalid policy: 409
  `policy_unresolved`, nothing saved.
- Database: `blood_requests.0001_initial`. CHECK constraints for quantity 1–100, 0 ≤ fulfilled ≤ quantity and
  all four enums. The requester FK is PROTECT: request history is never deleted with an account, so deactivate
  the account instead.
- Provisioning: `python backend/manage.py provision_requester --email <x@example.test>` creates a new REQUESTER
  (DEBUG/local only, password from `REQUESTER_PASSWORD`, never printed, never changes an existing role);
  `--deactivate` deactivates one. There is no HTTP endpoint.
- Form: `/requests/new`, using the shared `apiFetch` and CSRF flow unchanged. Rendering uses `textContent` only;
  the confirmation shows the saved request ID returned by the API.

## Integration notes and limits

- No notification intent is written on submission (notification policy unresolved; provider not on main).
- `GET /api/v1/requests` and request detail are BB-18/BB-19; there is no list page yet, so the requester
  identifies a request by the ID shown in the confirmation.
- No navigation link was added to `base.html`; open `/requests/new` directly.
- No browser-based UI test was run; the page JS is tested with a controlled DOM and a TEST-ONLY fake API, and
  the API is tested end to end on PostgreSQL.
